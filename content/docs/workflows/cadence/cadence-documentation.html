Purpose

A four-antenna digital beamformer with AD-FMCOMMS8 and an Agilex 5 board and actuated by a metamaterial deflector.

What a channel represents, where weights are applied, how channel identity is preserved, which synchronization assumptions apply, and what observations support the claimed behavior. Four antennas alone does not specify the number of independent spatial streams or establish a complete MIMO implementation.

Analog Devices’ FMCOMMS8 documentation identifies two ADRV9009 transceivers, four transmit and four receive channels, an FMC HPC connection, and JESD204B data transfer. The exact Agilex carrier’s electrical, clocking, interface, and reference-design compatibility remains an integration question.

What the references contribute

Reference Useful contribution to this specification Boundary
SPEAR-BF repository A concrete example connecting beamforming, hardware/software control, synchronization, calibration, and experimental observations. Its implementation targets Xilinx RFSoC ZCU216 and the CHARM frontend. Its IP, board configuration, and reported performance do not establish an Agilex/FMCOMMS8 port.
SPEAR-BF beamformer model The reviewed code makes array geometry and calibration inputs explicit when preparing beamforming weights. Reviewed as source; not executed or validated here.
Digital VLSI Architectures for Beam-Enhanced RF Aperture Arrays, IEEE TAES, 2015, DOI Relates beam enhancement to distinct prefiltering, steering, phase-compensation, and beamforming subsystems; discusses hardware verification and synthesis. The paper uses Virtex-6 and reports standard-cell synthesis for selected subsystems. It does not demonstrate this proposed four-channel hardware combination.

The paper’s architecture can help explain why the problem has multiple interacting parts. Implementing its complete prefiltering architecture is not a requirement adopted by this note. No equations or performance figures are imported into the proposed payload.

BIST is a required specification topic

BIST makes a fundamental question concrete: what can the design establish about itself, through which internal test mechanism, and within which fault model?

Topic Verified documentation Proposed use
Logic BIST Genus DFT guide, chapter “Inserting Logic Built-In-Self-Test Logic,” beginning at printed page 955. Explain stimulus generation, response analysis, test control, and the relationship between a fault model and the evidence produced.
Memory BIST Genus/Modus PMBIST Guide, including architecture, insertion, and verification sections. Identify how a memory test is specified and what a test result says about the memory being examined.
ADC BIST Ramp Generator for ADC Built-In-Self Test, a research paper describing a Cadence-based ramp-generator study. A related mixed-signal example. This is not a Genus/Xcelium manual or evidence that FMCOMMS8 implements that scheme.
Boundary scan Genus/Modus boundary-scan lab. Explain test access and interconnection concerns while keeping boundary scan distinct from logic or memory BIST.

For the beamformer mock-up, a candidate self-test story is: define a digital block under test, supply a known internal stimulus, observe a defined response, and record both the result and its limits. The specification must identify the faults it intends to detect and the RF, timing, and calibration questions that require other evidence. Choosing the actual BIST architecture remains design work. Cadence ASIC test insertion does not by itself supply an FPGA or RF-board self-test implementation.

A small workspace illustration

The existing Vivado notes provide a local organizational precedent. The following is a proposed layout only; no tool installation or executable flow is created by this note.

cadence/
  ai-tools/       task scope, documentation lookup, result interpretation
  references/     links to the existing vendor documentation
  work/
    beamformer/   payload specification, later RTL, testbench, and BIST design
  evidence/       outputs from identified runs, when runs actually exist
Step Architectural question Proposed evidence
Define the task Which requirement, assumptions, and part of the payload are in scope? A bounded task description tied to the specification.
Prepare the check Which tool function answers that question, and what inputs does it require? Relevant manual section, selected inputs, and an explicit expected result.
Simulate Does the modeled behavior meet the selected requirement? Xcelium logs, observations, and comparison results from an identified run.
Synthesize and examine testability How is the digital design represented in the selected technology, including the chosen test structures? Genus reports and, where the selected flow requires it, Modus BIST/test evidence.
Interpret What does the result establish, and what is still unresolved? An engineering assessment linked to the requirement and the actual output.

The Cadence path supports simulation, synthesis, and DFT questions. Agilex FPGA implementation belongs to its Quartus Prime toolchain. These paths can share a conceptual payload and selected design sources, while retaining their target-specific interfaces, libraries, constraints, and acceptance criteria.

This note and its inventory are under docs/workflows/cadence/. The PDFs remain at their original paths. No Cadence tool, FPGA build, simulation, synthesis, BIST insertion, or hardware experiment was run.
