Candidate concept-lineage graph schema

Author

Fernando Lessa Magalhães

Updated

September 14, 2026

Status of this artifact

artifacts/lineage-graph-candidate.json is a candidate temporal model derived bottom-up from artifacts/transcript/raw-transcript.md.

It is not a golden model. It has no authority over the existing concept Markdown files. Those files were not used to invent, select, or normalize graph nodes or edges. They may be compared with this graph only after the graph has been independently checked for semantic fidelity and structural consistency.

The graph covers only the transcript’s recorded evidence boundary: four calls, transcript segments 0001 through 1026, and source ordinals 2 through 5838. A later or earlier unrecorded exchange can extend or correct the candidate.

Modeling unit

The graph models a concept state, not a glossary term.

A concept state is one materially distinct point in a concept’s temporal lineage. A concept can therefore have several nodes: emergence, interpretation, correction, contextual rebinding, accepted working meaning, and unresolved branch.

Nodes do not collapse user statements, assistant interpretations, corrections, and acceptance into one timeless claim. Edges preserve how one state leads to another.

Root object

The JSON root contains:

  • schema_version: Version of this repository-local model.
  • artifact_id: Stable identifier for the graph artifact.
  • status: Must remain candidate until an explicit validation and promotion decision.
  • title: Human-readable description.
  • source: Controlling transcript and evidence boundary.
  • derivation: Method and authority limits.
  • status_registry: Allowed node statuses.
  • relation_type_registry: Allowed and documented edge meanings.
  • nodes: Concept-state nodes.
  • edges: Typed temporal and cross-concept relations.
  • uncertainties: Known limits that must survive later validation.

Node schema

Every node requires these fields:

Field Type Meaning
id string Stable, unique identifier. The identifier persists if wording is refined.
concept string Concept lineage to which the state belongs.
state_summary string Concise attributed summary of the state or claim.
lineage_position string Descriptive position such as emergence, correction, current working rule, or open branch. It is not an authority status.
source_segment_anchors non-empty array Exact transcript anchors supporting the state.
speaker string Primary attributed speaker: user, assistant, or mixed.
attribution string Explanation of who originated, interpreted, corrected, or accepted the state.
status enum Evidence and adoption status defined below.
call_order object First and last call, segment, and source ordinal covered by the state.

Each node source anchor contains:

  • call: Call number.
  • segment: Zero-padded transcript segment identifier.
  • source_ordinal: Original source ordinal.
  • role: Recorded transcript role.
  • function: Evidentiary function such as definition, correction, proposal, or explicit_acceptance.

call_order contains first_call, first_segment, first_source_ordinal, last_call, last_segment, and last_source_ordinal. These values support deterministic temporal sorting without replacing the exact source anchors.

Node status semantics

The allowed statuses are intentionally narrow:

  • attested: Directly present in the transcript and attributed to its speaker. It does not imply universal truth or final adoption.
  • assistant-proposed: An assistant formulation or taxonomy without direct user acceptance in the captured evidence.
  • user-corrected: The user explicitly corrected, narrowed, or rebound a preceding formulation. The node summary follows that correction.
  • user-accepted: An assistant or mixed formulation with direct user acceptance in a cited user segment. Every such node must contain a user anchor whose function begins with explicit_acceptance.
  • unresolved: The transcript leaves a conflict, incomplete explanation, missing validation, or open branch.

Polite acknowledgements are not automatically acceptance. Acceptance is used only when the local exchange directly treats the formulation as correct, governing, or the basis for continuation.

Edge schema

Every edge requires:

Field Type Meaning
id string Unique stable edge identifier.
from string Existing source node identifier.
to string Existing target node identifier.
relation enum A relation documented in relation_type_registry.
source_segment_anchors non-empty array Transcript evidence for the transition or cross-concept relation.
attribution string Who made or supports the relation and what must not be inferred from it.

The graph currently uses these relation types:

  • emerged_from: The target becomes a distinct concept state through the source episode.
  • interpreted_as: The target is an attributed interpretation of the source.
  • corrected_by: The source is explicitly corrected or narrowed by the target.
  • rebound_in_context: The concept or relation receives a new context-specific binding.
  • derived_from: The target follows analytically without claiming identity.
  • explicitly_accepted: The target is directly accepted by the user at a cited segment.
  • remains_unresolved: The target preserves an open or conflicting branch.
  • represented_as: One domain or concept is expressed in another representation, such as a domain represented by a directory.
  • constrained_by: The target bounds the valid scope of the source.
  • motivates: The source supplies the reason for the target.
  • distinguished_from: The target is explicitly separated from the source.
  • governs: The source supplies operative interpretation or production rules for the target.

Relation direction is semantically significant. For example, A corrected_by B means B is the corrected state, and A represented_as B means B is the representation.

Uncertainty schema

Every uncertainty requires:

  • id: Unique uncertainty identifier.
  • summary: What is not settled.
  • source_segment_anchors: Evidence that the limit exists.
  • impact: What later work must not infer until the uncertainty is resolved.

Uncertainties are part of the model, not validation noise. Promotion must not delete them merely to obtain a cleaner graph.

Structural invariants

A valid candidate graph must satisfy all of the following:

  1. The JSON parses successfully.
  2. Node, edge, and uncertainty identifiers are unique in their own collections.
  3. Every node contains all required fields and at least one source anchor.
  4. Every edge references existing nodes and uses a documented relation type.
  5. Every source anchor resolves to a segment in the controlling transcript with the same call and source ordinal.
  6. Every node status belongs to status_registry.
  7. Every user-accepted node contains a direct user acceptance anchor.
  8. Node call/order bounds match the first and last source anchors.
  9. No structural cycle is automatically treated as an error. Conceptual rebinding can legitimately revisit an earlier concept; temporal order remains in source anchors.
  10. status remains candidate until semantic validation is complete.

Semantic validation and promotion gate

Structural validity is necessary but not sufficient. Before any promotion, an independent review must:

  1. Compare every node summary with all cited transcript segments.
  2. Check that omitted nearby segments do not reverse or materially narrow the summary.
  3. Confirm attribution, especially user-accepted and user-corrected states.
  4. Check each edge direction and relation type against conversational order.
  5. Resolve or explicitly retain each uncertainty.
  6. Compare existing concept Markdown files against the validated graph and report discrepancies without allowing those files to retroactively change transcript-derived evidence.
  7. Obtain an explicit decision to designate a validated revision as the golden model.

Until all gates pass, downstream comparison may identify differences, but the candidate graph must not be used to overwrite domain files.

Current candidate inventory

At initial construction, the candidate contains:

  • 66 concept-state nodes.
  • 67 typed edges.
  • 21 distinct concept labels.
  • 7 explicit uncertainties.

These counts are descriptive and must be regenerated after any edit.

Initial structural validation

The initial candidate passed these checks:

  • jq JSON parsing and schema assertions.
  • Unique node, edge, and uncertainty identifiers.
  • Valid node statuses and documented edge relations.
  • Existing endpoints for every edge.
  • A direct user acceptance anchor for all 21 user-accepted nodes.
  • Matching call/order bounds for every node.
  • 446 graph anchors resolved against all 1,026 indexed transcript segments with matching call and source ordinal; node anchors also matched the recorded role.
  • Wolfram graph inspection found 66 vertices, 67 directed edges, one weakly connected component containing all 66 vertices, no self-loops, no isolated vertices, and no directed cycles.

This is structural validation only. It does not satisfy the semantic validation and promotion gate above.
