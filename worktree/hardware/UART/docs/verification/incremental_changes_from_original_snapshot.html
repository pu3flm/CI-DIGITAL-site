Incremental Changes From Original Snapshot

Author

Fernando Lessa Magalhães

Updated

September 14, 2026

Scope Of This Comparison

Comparison base:

  • original_snapshot/sim/

Compared against:

  • current sim/

Reference note:

  • original_snapshot/rtl/ also exists, but this incremental record is centered on verification-side evolution in sim/, which is the intended implementation area for this work.
  • original_snapshot/baudrate_test.sv was used only as a side-check of direction, not as the main reference.
  • original_snapshot/config.tcl was used only as a side-check for environment/test invocation.

High-Level Evolution Story

The original snapshot was an incomplete proto-UVM environment with a clear RX baseline path and partial or blank TX-side pieces.

The current submission continued that structure rather than replacing it.

The main evolution was:

  1. preserve the original baseline communication path
  2. complete the missing symmetric TX-side verification structure
  3. keep BFMs and uvm_config_db as the driving/observation mechanism
  4. extend item, drivers, monitors, coverage, and tests only where required for the chosen baud/parity objectives
  5. document the observed simulation results with evidence

Short reading:

  • original snapshot: one clear RX-oriented starting path, with TX still partial
  • current submission: same architecture, but completed into a two-sided communication environment with focused baud/parity extensions

File-Level Comparison

Files present only in the current sim/

  • sim/baud_sequence.sv
  • sim/parity_sequence.sv
  • sim/scoreboard.sv
  • sim/coverage.sv
  • sim/artifacts/
  • sim/tools/

Meaning:

  • the current tree adds focused stimulus for baud and parity
  • the current tree consolidates checking and coverage into reusable generic classes used on both RX and TX sides
  • support tooling and saved evidence were added to make the work reproducible

Files present only in the original snapshot

  • original_snapshot/sim/rx_scoreboard.sv
  • original_snapshot/sim/rx_coverage.sv

Meaning:

  • the original snapshot had dedicated RX-only scoreboard and coverage classes
  • the current submission did not bypass that idea; it generalized it into shared scoreboard.sv and coverage.sv, then instantiated one per side inside the environment

Important Structural Differences

1. Environment

Original:

  • original_snapshot/sim/environment.sv:7-45
  • RX side only is effectively assembled
  • TX-side environment composition is absent

Current:

  • sim/environment.sv:7-63
  • RX and TX sides are both present
  • each side has:
    • one agent
    • one scoreboard
    • one coverage instance
  • both sides are connected through analysis ports/fifos in the same proto-UVM style

Interpretation:

  • this is a coherent continuation of the original direction
  • the current work completed the intended symmetric architecture instead of replacing it

Why it matters:

  • the original diagram/test intent already suggested RX/TX symmetry
  • the current submission did not invent a new environment shape; it filled in the missing side so the intended communication path could really be exercised end-to-end

2. Baseline Test

Original:

  • original_snapshot/sim/test.sv:19-33
  • only rx_ag is activated
  • one random sequence is started on the RX sequencer

Current:

  • sim/test.sv:21-45
  • both rx_ag and tx_ag are activated
  • random sequences are started on both sequencers
  • the test now waits for scoreboard accounting before finishing

Interpretation:

  • the baseline was strengthened into a true two-sided communication reference path
  • the original intent was preserved, but the execution became more complete and measurable

Send / Expect / Observe difference:

  • original snapshot:
    • sends one random sequence through the RX side only
    • expects only the RX-side baseline to be active
    • does not explicitly wait for scoreboard accounting before ending
  • current submission:
    • sends random traffic on both RX and TX sides
    • expects both sides to participate in the baseline communication path
    • waits until the scoreboard confirms that all generated items were checked

3. TX-Side Verification Completeness

Original:

  • original_snapshot/sim/tx_agent.sv is blank
  • original_snapshot/sim/tx_sequencer.sv is blank
  • original_snapshot/sim/tx_driver.sv:23-25 is to do
  • original_snapshot/sim/tx_monitor.sv:27-45 is only partially implemented

Current:

  • sim/tx_agent.sv
  • sim/tx_sequencer.sv
  • sim/tx_driver.sv
  • sim/tx_monitor.sv

Interpretation:

  • the current submission completed the missing TX verification path locally and minimally
  • this is one of the clearest examples of continuing the original scaffold rather than drifting away from it

Why it matters:

  • this is not a cosmetic change
  • it is the concrete step that turns the original partial scaffold into a real two-sided verification environment

4. Item Model

Original:

  • original_snapshot/sim/uart_item.sv:11-15
  • only data[7:0]

Current:

  • sim/uart_item.sv:11-80
  • retains data
  • adds only the configuration needed for the chosen tests:
    • parity fields
    • stop-bit field
    • data length field
    • baud-rate code
    • parity-error injection flag

Interpretation:

  • this is a natural item-level extension for baud/parity scenarios
  • it is not a structural rewrite; it is a local completion so the next tests can be expressed through the existing architecture

Why it matters:

  • the original item could express only byte traffic
  • the current item can still express the same byte traffic, but now also carries exactly the configuration needed for the chosen new scenarios

5. BFM and Monitor Behavior

Original:

  • RX-side command/result observation was present
  • configuration-aware decode was not carried through for the new scenarios
  • parity-error injection support was not present in uart_bfm.send()

Current:

  • sim/uart_bfm.sv adds optional parity-error injection
  • sim/reg_if_bfm.sv mirrors active configuration so monitors can decode according to current settings
  • sim/rx_monitor.sv and sim/tx_monitor.sv decode with the active configuration after the observed frame start edge

Interpretation:

  • these are local, architecturally natural monitor/driver/BFM extensions for the new verification goals

Why it matters:

  • the new tests are still exercised through the existing BFMs and monitor path
  • the work did not bypass the architecture by turning the tests into direct DUT pokes

Behavioral Differences By Purpose

Baseline Stabilization

Compared with the original snapshot, the current submission improved the baseline by:

  • activating both agents
  • completing the TX path
  • synchronizing end-of-test with scoreboard accounting
  • keeping the same command/result scoreboard concept

Practical effect:

  • the baseline changed from a partial scaffold into a stable reference run used to anchor the later baud/parity investigations

Baud Verification Support

Compared with the original snapshot, the current submission added:

  • baud-capable item fields
  • baud_sequence.sv
  • uart_baud_test
  • uart_baud_boundary_test
  • configuration-aware decode in the monitors
  • saved evidence logs and one failing waveform for the boundary case

Practical effect:

  • baud verification is no longer only an idea suggested by the repository clues
  • it became a real, runnable path with a characterized pass/fail boundary

Parity/Error Verification Support

Compared with the original snapshot, the current submission added:

  • parity-capable item fields
  • parity-error injection through the UART BFM
  • parity_sequence.sv
  • uart_parity_test
  • explicit check that serial parity corruption is visible while the DUT-visible rx_error status remains absent

Practical effect:

  • parity/error behavior is now tested through the same proto-UVM path as the baseline communication case
  • the final result is evidence-based: the serial parity error is present, but the DUT-visible status path does not expose it

Side Check: original_snapshot/baudrate_test.sv

This file was not used as the main reference, only as a direction check.

Observed direction in that file:

  • it targets baud variation explicitly
  • it reconfigures the UART per test iteration
  • it uses random traffic to exercise different baud settings

Comparison with the current submission:

  • the current submission took the same verification direction: baud-rate behavior is one of the focused new tests
  • however, the current implementation is more aligned with the existing proto-UVM architecture because it carries baud configuration through the item / sequence / driver / monitor path instead of using direct test-level BFM poking as the main method

Direct reading:

  • same theme: yes
  • same implementation style: no
  • current submission is more consistent with the repository architecture

Conclusion:

  • the current work follows the same natural verification theme
  • it is at least as aligned with the repository direction, and more architecturally coherent with the proto-UVM structure already present in sim/

Side Check: original_snapshot/config.tcl

Relevant observation from original_snapshot/config.tcl:47-53:

  • the original environment expected separate compilation of:
    • test.sv
    • parity_test.sv
    • baudrate_test.sv
    • testbench.sv

Current situation:

  • current automation compiles sim/test.sv and sim/testbench.sv
  • the focused tests are implemented as classes inside sim/test.sv
  • they are selected through UVM_TESTNAME, so separate .sv files are not required

Relevant UVM/env flags from the original config:

  • UVM_TEST
  • UVM_VERBOSITY
  • RND_SEED

Current automation still supports the same important controls through the root Taskfile.yml flow.

Conclusion:

  • no important original UVM runtime control appears to have been lost
  • the main difference is packaging: current tests are class-defined in one file instead of spread across separate test files

Why it matters:

  • this confirms that the current submission did not miss an obvious runtime control from the older setup
  • the difference is organizational, not a loss of verification capability

Utility Of original_snapshot/rtl/

original_snapshot/rtl/ is useful only as a historical baseline reminder of the DUT shape.

For this submission comparison, its practical value is limited because:

  • the current work scope is verification-side evolution in sim/
  • the submission intentionally did not use rtl/ as the main implementation area

The main useful comparison is the sim/ tree, not the historical RTL snapshot.

Final Comparison Conclusion

From the original snapshot to the current submission, the verification evolution can be summarized as:

  • original snapshot:
    • working RX-centered baseline scaffold
    • partial or blank TX-side pieces
    • no completed focused baud/parity test flow integrated end-to-end
  • current submission:
    • symmetric RX/TX environment completed
    • baseline path stabilized and passing
    • focused baud and parity/error tests added through the existing architecture
    • simulation evidence captured and documented
    • remaining failures separated into:
      • testbench issue that was fixed (stale baud monitor decode)
      • DUT-visible limitations that remain (high-baud limit and parity-status visibility)

This is a coherent continuation of the original proto-UVM direction, not a structural reinvention.

One-line conclusion:

  • the original snapshot provided the proto-UVM direction
  • the current submission completed only the missing pieces needed to make that direction runnable, testable, and “evidence-backed”
