SIM Architecture Study

Author

Fernando Lessa Magalhães

Updated

September 14, 2026

Reference Frame

This repository is treated as an evolving proto-UVM snapshot.

  • rtl/ is the DUT truth.
  • sim/ is the verification evolution area.
  • The baseline communication path is preserved as the reference path.
  • Blank or partial files in sim/ are not completed unless they are needed.

Diagram Comparison

20260415194238.png Top/Testbench Diagram

Expected by the diagram:

  • top-level DUT instance
  • reg_if_bfm
  • uart_bfm
  • uvm_config_db used to distribute the BFMs

Observed in sim/testbench.sv:

  • uart_bfm bfm_uart0(); and reg_if_bfm bfm_reg0(); are instantiated at top level (sim/testbench.sv:8-9)
  • uart_controller dut (...) is instantiated and connected to the register side through bfm_reg0 and to the UART side through bfm_uart0 (sim/testbench.sv:11-25)
  • both BFMs are published through uvm_config_db with wildcard scope (sim/testbench.sv:27-30)

Conclusion:

The implementation matches the top/testbench diagram.

20260415194213.png Verification Architecture Diagram

Expected by the diagram:

  • one test containing one environment
  • two symmetric agent sides: RX and TX
  • each side with sequencer, driver, and monitor
  • one scoreboard and one coverage block per side
  • scoreboard command/result FIFOs
  • BFMs distributed through uvm_config_db

Observed in sim/:

  • uart_test creates uart_environment (sim/test.sv:10-24)
  • uart_environment creates rx_ag, tx_ag, rx_scb, tx_scb, rx_cov, and tx_cov (sim/environment.sv:15-41)
  • each agent instantiates sequencer and driver only when active, and always instantiates a monitor (sim/rx_agent.sv:21-52, sim/tx_agent.sv:21-53)
  • each monitor publishes command and result streams (sim/rx_monitor.sv:14-25, sim/tx_monitor.sv:14-25)
  • each scoreboard owns two FIFOs: command_fifo and result_fifo, which are the implemented equivalents of the diagram command/result FIFOs (sim/scoreboard.sv:14-23)
  • the environment connects command streams to scoreboard plus coverage, and result streams to scoreboard (sim/environment.sv:43-58)
  • BFMs are retrieved from uvm_config_db inside agents, drivers, and monitors (sim/rx_agent.sv:39-49, sim/tx_agent.sv:39-50, sim/rx_monitor.sv:27-30, sim/tx_monitor.sv:27-30, sim/rx_driver.sv:18-22, sim/tx_driver.sv:18-22)

Conclusion:

The implementation matches the verification architecture diagram and the same architectural conclusion holds.

DUT Scope vs Verification Scope

DUT scope

  • uart_controller is the composed DUT under rtl/
  • register writes configure UART behavior
  • register reads return status and RX data

Verification scope

  • BFMs model the register interface and UART serial interface
  • agents split stimulus, driving, and monitoring
  • scoreboards compare expected command bytes against observed result bytes
  • coverage samples observed command bytes

Baseline Communication Path

RX side

  1. random_sequence generates a uart_item carrying one data byte (sim/random_sequence.sv:19-31, sim/uart_item.sv:8-17)
  2. rx_driver gets the item and drives serial stimulus through uart_bfm.send(command.data) (sim/rx_driver.sv:24-37)
  3. rx_monitor observes the serial command through uart_bfm.receive_rx(...) (sim/rx_monitor.sv:33-40)
  4. rx_monitor observes the DUT-visible result through reg_if_bfm.uart_receive(...) (sim/rx_monitor.sv:42-49)
  5. rx_scb compares command and result bytes (sim/scoreboard.sv:29-47)

TX side

  1. random_sequence generates a uart_item carrying one data byte (sim/random_sequence.sv:19-31, sim/uart_item.sv:8-17)
  2. tx_driver applies the baseline CSR configuration and sends the byte through reg_if_bfm.uart_send(command.data) (sim/tx_driver.sv:24-40)
  3. tx_monitor captures the command at the register side through reg_if_bfm.get_if_write01(...) (sim/tx_monitor.sv:33-41)
  4. tx_monitor captures the resulting UART frame through uart_bfm.receive_tx(...) (sim/tx_monitor.sv:43-50)
  5. tx_scb compares command and result bytes (sim/scoreboard.sv:29-47)

Top-level UVM flow

  • uart_test starts one random sequence on RX and one on TX (sim/test.sv:26-37)
  • the test waits until both scoreboards account for all generated items (sim/test.sv:38-42)

What Is Already Coherent (double checked :D)

  • The top/testbench composition matches the diagram and README description.
  • uvm_config_db is the actual virtual interface distribution mechanism.
  • Both RX and TX sides follow the same proto-UVM decomposition: sequencer, driver, monitor, scoreboard, coverage.
  • The baseline byte-to-byte communication flow is runnable and passing.

What Is Structurally Present But Still Baseline-Limited

  • uart_item carries only a data byte, so config-driven scenarios are not yet expressible in the item.
  • tx_driver hardcodes the baseline configuration through configure_csr(0, 0, 0, 0, 3'd7, 5'd21) (sim/tx_driver.sv:33), which corresponds to the current 8-bit, no-parity, one-stop-bit, baseline baud setting.
  • rx_driver, rx_monitor, and tx_monitor all use BFM defaults for baud/parity/stop behavior, so the present monitor/decode path is aligned to the same baseline profile.
  • scoreboard checks only raw byte equality.
  • coverage measures only byte-value coverage.

Next Extension Points

The next verification directions remain baud-rate behavior first, then parity/error behavior.

The minimal extension path inside the current architecture is:

  1. extend uart_item with only the configuration fields required by the chosen tests
  2. add focused sequences that generate those settings and data combinations
  3. update drivers so the BFMs and CSR configuration are driven from the item instead of fixed defaults
  4. update monitors only where additional observed information is required for the new checks
  5. extend scoreboard so pass/fail remains explicit for baud/parity scenarios
  6. add focused coverage tied to baud/parity intent rather than generic protocol boilerplate

Current Architectural Conclusion

The current repository state follows the same conclusion as the README and the two diagrams:

  • 20260415194238.png explains the instantiated top/testbench connectivity
  • 20260415194213.png explains the internal verification architecture
  • the implemented sim/ code preserves that proto-UVM direction
  • the next work should stay concentrated in sim/ and extend the existing path rather than replace it
