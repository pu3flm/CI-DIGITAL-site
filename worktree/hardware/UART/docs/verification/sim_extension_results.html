SIM Extension Results

Author

Fernando Lessa Magalhães

Updated

September 14, 2026

Scope

This work stayed in sim/.

  • no rtl/ files were changed
  • no structural refactor was performed
  • the existing proto-UVM architecture was preserved
  • the baseline test remained the reference path

Changed Verification Files

  • sim/uart_item.sv
  • sim/uart_bfm.sv
  • sim/reg_if_bfm.sv
  • sim/rx_driver.sv
  • sim/tx_driver.sv

  • sim/baud_sequence.sv
  • sim/parity_sequence.sv

Added

Item-level configuration support

sim/uart_item.sv:11-80 now carries the minimum fields needed for the new tests:

  • parity_enable
  • parity_type
  • stop_bit
  • data_len
  • baud_rate_code
  • inject_parity_error

The same file also provides:

  • get_data_len()
  • get_baud_rate()
  • get_parity_mode()

BFM support for parity error injection

sim/uart_bfm.sv:75-117 extends the existing send() task with inject_parity_error so the RX path can receive a deliberately wrong parity bit without bypassing the BFM path.

Shared configuration shadow in the register BFM

sim/reg_if_bfm.sv:25-38 and sim/reg_if_bfm.sv:203-227 now keep the active UART configuration mirrored in the verification side:

  • current baud-rate code and real baud value
  • current data length
  • current parity mode
  • current stop-bit mode

This lets monitors decode serial traffic according to the same configuration written through the register interface.

Driver and monitor extensions

  • sim/rx_driver.sv:32-40 now drives the serial RX path with the item-selected baud, length, parity, stop-bit, and parity-error injection.
  • sim/tx_driver.sv:24-70 now applies CSR configuration from the item and only rewrites the DUT configuration when it changes.
  • sim/rx_monitor.sv:35-55 now decodes command traffic using the mirrored register configuration and tracks observed rx_error events.

Focused coverage additions

sim/coverage.sv:19-60 still samples byte traffic, and now also samples:

  • baud_rate_code
  • parity_enable
  • parity_type
  • rx_error

New focused sequences and tests

  • sim/baud_sequence.sv:9-41
  • sim/parity_sequence.sv:9-43
  • sim/test.sv:49-156

New tests added:

  • uart_baud_test
  • uart_parity_test

Run Commands

  • Baseline: task run-baseline
  • Baud test: task run-test UVM_TEST=uart_baud_test
  • Parity test: task run-test UVM_TEST=uart_parity_test

2. Baud Test: Baseline And Mid-Range Baud Batches Pass, Highest Tested Baud Fails

Evidence from docs/verification/logs/xsim_uart_baud_test.log:

  • test seed TX transaction passes at baseline config: docs/verification/logs/xsim_uart_baud_test.log:53-55
  • RX batch at baud code 21 starts and matches cleanly: docs/verification/logs/xsim_uart_baud_test.log:56-104
  • RX batch at baud code 24 also starts and matches cleanly: docs/verification/logs/xsim_uart_baud_test.log:105-153
  • next RX batch starts at baud code 29: docs/verification/logs/xsim_uart_baud_test.log:154-155
  • the first remaining mismatch now appears at baud code 29: docs/verification/logs/xsim_uart_baud_test.log:156-157
  • fatal summary: docs/verification/logs/xsim_uart_baud_test.log:161-165

Observed baud-test conclusion:

  • the current snapshot remains coherent at the baseline baud path (115200, code 21)
  • after fixing the monitor-side stale-config race, the next exercised baud step (230400, code 24) is also coherent
  • the remaining observed baud failure is now at the highest tested step in this run (921600, code 29)
  • the failure remains observable in the command/result comparison path, not just in a narrative claim

Send / Expect / Observe summary:

  • what the test sends:
    • on the RX side, the BFM injects one serial frame per uart_item using the selected baud_rate_code from the sequence item
  • what the scoreboard expects:
    • the command monitor reconstructs the byte from the serial command path and sends that byte into command_fifo
  • what is actually observed:
    • the result monitor reads the DUT-facing byte back through the register interface and sends that byte into result_fifo
  • what the failing case shows:
    • at baud code 29, the transmitted and expected command byte is 0x74, while the DUT-visible observed result is 0xb8

Current interpretation:

  • baud variation is implemented in the verification environment
  • the monitor-side stale-config decode race was removed by decoding with the current register configuration only after the observed start edge
  • the current repository snapshot now sustains the baseline and mid-range tested baud steps, but still fails at the highest exercised baud step
  • this is now a reproducible verification result, not an assumption

Issue ownership reading:

  • the previous stale-config monitor race is no longer present, which is visible because baud code 24 now compares cleanly (docs/verification/logs/xsim_uart_baud_test.log:105-153)
  • the first remaining failing item is at baud code 29, with transmitted/expected command 0x74 and DUT-observed result 0xb8 (docs/verification/logs/xsim_uart_baud_test.log:154-157)
  • in the implemented architecture, the expected side comes from rx_monitor.command_monitor_task() (sim/rx_monitor.sv:35-69)
  • the actual side comes from rx_monitor.result_monitor_task() through bfm_reg0.uart_receive(...) (sim/rx_monitor.sv:47-55)

Therefore the current remaining baud failure no longer points to the stale serial decode issue.

With the monitor race removed, the remaining mismatch points to the DUT-facing receive/status path or to an overall high-baud limit in the current snapshot.

3. Parity Test: Injected Parity Error Is Seen on the Serial Side, But rx_error Is Not Observed in the DUT Status Path

Evidence from docs/verification/logs/xsim_uart_parity_test.log:

  • TX seed transaction with parity enabled passes: docs/verification/logs/xsim_uart_parity_test.log:54-55
  • RX parity-error sequence starts: docs/verification/logs/xsim_uart_parity_test.log:56-59
  • repeated parity-bit mismatch is detected by the UART BFM on the injected RX traffic: docs/verification/logs/xsim_uart_parity_test.log:60, 64, 68, and continuing through 180
  • despite the injected parity mismatch, the RX scoreboard still sees byte-for-byte data matches: docs/verification/logs/xsim_uart_parity_test.log:61-62, 65-66, and continuing through 181-182
  • the explicit parity-status check then fails because rx_error_count stays 0: docs/verification/logs/xsim_uart_parity_test.log:183
  • fatal summary: docs/verification/logs/xsim_uart_parity_test.log:187-191

Observed parity-test conclusion:

  • parity-error injection is working on the serial stimulus path :D
  • the received byte still propagates through the current DUT/register path
  • the expected DUT-visible parity-error status is not observed in the current snapshot

Send / Expect / Observe summary:

  • what the test sends:
    • TX seed case sends one parity-enabled frame without corruption
    • RX parity case sends parity-enabled frames with deliberate parity-bit corruption
  • what the scoreboard expects:
    • byte data should still match if the DUT continues to capture the frame payload
  • what is actually observed:
    • the serial monitor reports parity mismatches on the injected RX traffic
    • the RX scoreboard still sees matching command/result bytes
    • the monitor-side rx_error_count remains 0
  • what the failing case means:
    • the parity violation is real on the serial path, but it does not become visible through the DUT status path used by the test

Current interpretation:

  • the parity/error test is useful because it separates three facts:
    • the serial parity corruption is real
    • the byte data path still completes
    • the status/error path does not currently reflect the expected parity-error event

Issue ownership reading:

  • parity corruption is injected in the BFM send path by flipping the parity bit (sim/uart_bfm.sv:95-106)
  • the serial-side monitor then repeatedly reports parity mismatches in the saved run log (docs/verification/logs/xsim_uart_parity_test.log:60, 64, 68, and onward)
  • at the same time, the RX scoreboard continues to receive matching command/result bytes (docs/verification/logs/xsim_uart_parity_test.log:61-62, 65-66, and onward)
  • the explicit failure occurs only when the monitor-level rx_error_count check remains 0 (docs/verification/logs/xsim_uart_parity_test.log:183)
  • in the implemented monitor path, rx_error_count depends on bfm_reg0.rx_error becoming visible during uart_receive() (sim/rx_monitor.sv:47-55)

Therefore the parity test failure points primarily to the DUT-visible error/status path, not to the parity-error stimulus path itself.

The serial path clearly sees the parity violation, but that condition is not becoming observable through the current register/status path used by the verification environment.

Current Status Of The Verification Evolution

The verification-side extension is now in this state:

  • baseline communication path: stable and passing
  • focused baud-rate extension: implemented and simulation-backed, with stable results at codes 21 and 24, and a remaining mismatch at code 29
  • focused baud boundary characterization: completed, with highest passing code 24 and first failing code 25
  • focused parity/error extension: implemented and simulation-backed, but exposes missing observable rx_error behavior in the current snapshot

Technical Reading

The current work stayed aligned with the original proto-UVM direction:

  • changes remained concentrated in sim/
  • BFMs and uvm_config_db remained the mechanism for driving and observing behavior
  • new scenarios were added through item, sequence, driver, monitor, coverage, and test layers already present in the repository
  • the conclusions are tied to simulation evidence rather than unsupported claims

The result is not a structural rewrite. :D

It is a minimal continuation of the existing verification scaffold that preserves the baseline path and reveals the current non-baseline limits of the snapshot.

Current Fault Separation

With the current evidence, the two non-baseline failures separate as follows:

  • baud-rate failure at the highest tested baud step:
    • primary ownership now points to the DUT-facing receive/status path or to an overall high-baud limit in the current snapshot
    • reason: after removing the stale monitor decode race, codes 21 and 24 compare cleanly, while code 29 still returns a different DUT-observed byte than the transmitted command
  • parity/error visibility failure:
    • primary ownership points to the DUT-visible error/status path
    • reason: the parity corruption is real on the serial path, but the expected rx_error indication does not become observable through the current status path
