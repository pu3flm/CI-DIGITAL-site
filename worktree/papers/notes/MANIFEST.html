Our Foremost Definition

Object Methodology

  • Focus: how to build the software structure
  • Unit: class, object, method, interface, interaction
  • Main question: How should the system be organized in code?

Ontology Methodology

  • Focus: how to define the domain and its concepts
  • Unit: concept, relation, property, constraint, role, category
  • Main question: What exists in the domain, what does it mean, and how does it relate?

Role

Object methodology gives you executable architecture. Ontology methodology gives you conceptual architecture.

Difference

Object methodology asks:

  • What software entities should exist?
  • What responsibilities should they hold?
  • How do they collaborate with our intent?

Ontology methodology asks:

  • What domain entities should be recognized?
  • What distinctions matter?
  • What relations and constraints define the domain?
  • What terminology should be stabilized?

So:

object methodology = organization of code artifacts

ontology methodology = organization of domain knowledge

Why in Verification?

Verification sits between a technical implementation world and a semantic/domain world, and that is why they are often mixed. Verification engineers constantly move between:

  • protocol concepts
  • requirements
  • transactions
  • error classes
  • coverage intent
  • testbench architecture
  • reusable software components

This causes confusion, but these are valid and necessary transitions. It is our job to move between these realms.

A verification engineer may ask:

What is a transaction?

This can mean:

  • Ontologically: what kind of domain concept is a transaction?
  • Object-methodologically: what class should represent a transaction in code?

These are different questions.

Terminology Shift Signals

  • interface in ontology discussion = a conceptual role/contract
  • interface in OOP = a programming construct for behavioral contract
  • interface in SystemVerilog hardware context = a signal bundle boundary

This is exactly the kind of context shift that causes drift. And SystemVerilog condenses too much at the runtime stratum, for God’s sake!

Comparison in This Context

Ontology Methodology in Verification

  • Defines what a transaction is
  • Distinguishes stimulus, observation, response, failure, coverage point, requirement
  • Defines relations such as:
    • test covers requirement
    • monitor observes transaction
    • scoreboard evaluates expected vs. actual
    • assertion constrains legal behavior

Object Methodology in Verification

Decides to represent those things with:

  • transaction class
  • monitor class
  • driver class
  • scoreboard class
  • sequence class
  • coverage collector object

So, one defines the domain map. The other defines the software structure that embodies part of that map. In this sense, ontology methodology answers what the world means and object methodology answers how the software should embody part of that world.

When does ontology come first? When:

  • We do not yet know what concepts matter
  • Our terminology is unstable
  • People use the same word differently
  • Requirements, tests, and coverage are poorly related
  • Failure categories are unclear
  • The team lacks a coherent conceptual map

In that situation, forcing classes too early can be misleading. We may encode confusion into software. We have seen this as factual evidence among our classmates. At least is an observable behavior.

Hence, we can assert that object methodology comes first when:

  • The domain concepts are already mostly stable
  • You need maintainable implementation
  • The challenge is reuse, modularity, substitution, and execution structure

This is where OOP/UVM demonstrates its strength, enabling efficient problem-space exploration through a well-established technique. However, object methodology cannot, by itself, guarantee:

  • correct domain distinctions
  • stable terminology
  • meaningful classification of failures
  • proper relation between intent and evidence
  • conceptual completeness

We can build elegant classes around a confused domain model. That is an important warning and highlights a key limitation: OOP by itself is a limited tool within the scope of Unified Verification Methodology and only partially addresses the core problems of the ASIC flow.

At the same time, ontology methodology cannot provide:

  • executable testbench structure
  • software modularity
  • lifecycle behavior
  • reusable implementation patterns
  • simulation-time coordination

This reveals that we can have a clear conceptual model and still produce poor code architecture. Therefore, we need a “code methodology.” OOP appears to be the best available tool for this task at present.

We can express the relationship as:

  1. Ontology methodology clarifies the domain.
  2. Object methodology implements a usable software structure from that clarified domain.

Not everything in the ontology becomes an object, and not every object corresponds to a first-class ontology concept. This distinction is essential.

The Scoreboard Example

If we examine a scoreboard, we can ask conceptual questions such as:

  • What is the role of a scoreboard in verification?
  • Is it a comparator, an evaluator, a source of evidence, a failure classifier?
  • What relation does it have to expected behavior and observed behavior?

These questions belong to the ontological domain. On the other hand, implementation-focused questions include:

  • Should the scoreboard be one class or several?
  • Should prediction and comparison be separated?
  • What methods should it expose?
  • How should it communicate with monitors?

These belong strictly to the object/implementation domain. They use the same terminology but operate at different levels of context.

The Underlying Pattern

These observations reveal a recurring pattern we often struggle with. Every such struggle should be examined carefully.

This leads to a deeper question: Why does verification eventually resemble an information problem?

This distinction helps answer that:

  • Ontology methodology appears when the pain is semantic confusion.
  • Object methodology appears when the pain is implementation complexity.

Verification at scale typically involves both.

The habit of treating verification as purely sequential scripting does not stabilize ontology and does not scale object architecture. When “abstract discussion” is dismissed as irrelevant, it is often precisely what should be addressed first.

Ontology should act as a disciplined guide, enabling effective use of objects to manipulate the problem domain in microelectronic engineering.

In other words:

  • Ontology determines what verification concepts exist and how they relate.
  • Object methodology determines how to realize those concepts in software for real-world systems.

In conclusion, this clarifies the distinction and yields a more coherent process:

(Question the domain meaning) -> (Select the structure that best serves that meaning)

And that is it.
