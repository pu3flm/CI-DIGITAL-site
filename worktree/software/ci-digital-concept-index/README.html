CI-DIGITAL Concept Index

Author

Fernando Lessa Magalhães

Updated

September 14, 2026

A deterministic, local-first Python and SQLite implementation of the evidence-first methodology in the concept graph methodology.

The application preserves separate immutable record families for source evidence, analytical observations, candidates, reviewed semantic claims, verification, validation, approval, releases, publication events, and lifecycle actions. It does not infer semantic truth from counts, does not use an LLM, does not call the network, and does not claim ontology status.

Runtime

  • CPython 3.11 or later.
  • SQLite 3.35 or later through Python’s standard-library sqlite3 module.
  • No third-party package, service, model, daemon, or network connection.
  • Writable state only under var/ and exports/ by default.

The authoritative runtime declaration is runtime.lock.json. The launcher is bin/ci-digital-concept-index.

Layout

bin/                  local launcher
config/               application, normalization, and environment examples
docs/                 requirements, architecture, policy, assurance, and operations
exports/              deterministic downstream files; ignored except .gitkeep
fixtures/             explicit bootstrap input and future negative-test design
migrations/           checksum-pinned SQLite schema, views, and guards
schemas/               JSON command-envelope contracts
src/                   standard-library Python package
var/                   local SQLite state; ignored except .gitkeep

Operator Sequence

All commands are explicit; none run automatically.

cd /home/fern/workspace/Inatel/CI-DIGITAL/worktree/software/ci-digital-concept-index

bin/ci-digital-concept-index status
bin/ci-digital-concept-index init
bin/ci-digital-concept-index record import \
  --input fixtures/bootstrap-registry.json
bin/ci-digital-concept-index validate all

The bootstrap is optional and is never evidence about a source corpus. Source acquisition records must be appended separately before extraction.

Explicit Workflow

  1. Append actors, versioned procedures/tools/configurations/environments, explicit configuration-to-procedure/tool applicability, acquisition activities, source identities, versioned source-routing decisions, source artifacts, and source versions.
  2. Run pipeline extract, segment, normalize, tokenize, ngrams, aggregate, observe, and isf with explicit JSON specs.
  3. Run workflow nominate-term or nominate-relation; an observation never changes type.
  4. Seal each positive non-vacuous claim profile and complete query/relevance set, then run workflow register-term, register-concept, and claim; candidates and claims keep distinct IDs.
  5. Run workflow review, create the immutable release-content candidate, then run verify, validate-use, evaluate-retrieval, and assure as separate release-relative acts.
  6. Run workflow finalize-release to freeze the complete post-V&V approval package, then an independent approve, then publish. A later package version must explicitly supersede the current package head for the same immutable release. The first channel success is bootstrap; later success is advance. Neither approval nor publication mutates release content.
  7. Use change, impact, deprecate, and retire to create new lifecycle records; canonical rows are never updated or deleted.

There is intentionally no promote, update, or delete command.

Mandatory Views

  • provenance_evidence_view
  • observation_graph
  • reviewed_semantic_graph
  • release_governance_view

observation_graph includes registered nodes before edges, so isolates survive, and exposes source-distribution scores as independent similarity_signal records. reviewed_semantic_graph includes concept definitions only through exact reviewed claim-to-definition bindings and includes only reviewed-accepted claims whose exact evidence profile and domain firewall pass. A projected edge remains an observation and copies its root evidence membership without adding independent support.

Safety Boundaries

  • Plain UTF-8 and Markdown extraction are identity imports. PDF, OCR, office, HTML, and external parser results must be produced elsewhere and imported with external_import, tool/version records, span maps, quality, and uncertainty.
  • Input and export paths are constrained to configured roots.
  • Ingested text is data only. The app never executes it, imports it as Python, evaluates it as SQL, or invokes a subprocess.
  • Every operational timestamp is supplied in a command spec. The app never invents acquisition, derivation, review, approval, or publication time.
  • Claim cid governance activates from explicit cid scope, a cid predicate, or either cid endpoint and requires exact active scope plus entity-level VLSI applicability/admission. ext: and ifc: remain separate schemes; scope none is only for sealed non-semantic profiles.
  • Release content and post-V&V approval packages have separate canonical artifact hashes. Packages form one immutable linear version chain per release; only its current head can be newly approved or published. Publication binds the approved package hash; exports include both identities and the frozen baseline snapshots.

Verification Status

Authoring validation is static only: source parsing, JSON/TOML parsing, inventory comparison, and migration checksum inspection. Per the implementation constraint, no test, application command, server, database initialization, migration execution, or fixture load was run. Runtime acceptance remains unverified until an operator executes the protocol in docs/ACCEPTANCE-CRITERIA.md.
