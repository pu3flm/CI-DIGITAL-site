Status Boundary

This file defines future operational acceptance. No test, app command, database initialization, migration execution, fixture load, or server was run during implementation. Static source/JSON/TOML/inventory/checksum inspection is not evidence that the runtime criteria pass.

The fixture plan is fixtures/pilot-negative-cases.json. It is deliberately declarative and must not be treated as observed evidence until instantiated and executed against authenticated test data.

Static Delivery Checks

ID Check Pass condition
ST-01 Python source parse Every .py parses through ast.parse; no module import or bytecode execution is required.
ST-02 Structured files parse Every JSON file parses, and pyproject.toml parses.
ST-03 Migration inventory Migration versions are unique/ordered; object names are unique; manifest hashes equal files.
ST-04 CLI/doc alignment Every advertised command exists in cli.py; all four mandatory views exist in SQL/export allowlist; invalid arguments route to canonical JSON stderr and exit 3.
ST-05 Table/code alignment Every table literal used by Python exists in migrations; every typed ID policy uses a constrained entity type.
ST-06 Runtime-state absence No .sqlite, .sqlite3, journal, WAL, generated export, or Python cache exists in the delivered tree.

Acquisition and Provenance

ID Required result
AP-01 100% of admitted segments traverse exact source artifact/input -> extraction run/output -> typed UTF-8 content identity and recomputed extracted-text hash -> segmentation input -> covering span -> identical half-open text slice and source version.
AP-02 100% of locally retained payload hashes recompute; unavailable artifact hashes carry explicit state and rationale.
AP-03 User, assistant, quotation, file, code, tool, system, and external classes remain query-separable.
AP-04 An assistant-only phrase has user TF/UF zero.
AP-05 Quoted VLSI text contributes to quotation/source views, never user-authored recurrence.
AP-06 Two records on one date with null sessions give date count one and SF unavailable.
AP-07 Mirror/quotation/summary/measure lineage remains traceable; every assessment member has one coherent class; claim-relative ISF collapses to one.
AP-08 Every cid segment/concept/claim resolves exact live target type, normalized typed facets, matching available basis-conditioned support, applicability, and accepted admission.
AP-09 Every source/derived artifact traverses the complete normalized acquisition/derivation spine, including source-routing history and matching acquisition status.
AP-10 Every dangling or inapplicable procedure/tool/config/environment/input/output/acquisition/run reference is rejected or release-blocking.
AP-11 Every derivation input explicitly records the exact observed identity state/hash/unavailable-rationale tuple; omission or disagreement with the artifact row is rejected.
AP-12 Text byte identity remains separate from extraction-bundle identity, and each aggregate/edge/similarity membership’s evidence/source/segment values resolve one exact provenance chain.
AP-13 Every release-item canonical record/hash recomputes; the non-recursive release-content hash equals manifest, artifact identity, and derivation output.
AP-14 Every approval-package version contains exactly the deterministic release-relative closure of definitions, labels/forms/facets, relations/predicates, mappings, sealed profiles/rules, approved uses, sealed query/relevance data, current V&V/retrieval, and assurance; later versions explicitly extend one current-head chain for the same release.
AP-15 A claim cannot bind an unsealed, changed, vacuous, zero-minimum, or wrong-version profile.

Deterministic Transformation

ID Required result
DT-01 Two clean runs with byte-identical inputs, configuration, IDs, and timestamps produce equal rows and hashes.
DT-02 Every normalized character and token span maps to raw source text; raw text is unchanged.
DT-03 A score-only change cannot alter evidence membership, ISF, claim events, approval, or publication.
DT-04 Reconstructed observation_graph has exactly all registered nodes, including the isolate, and independent records for every source-distribution similarity signal.
DT-05 Projection lists source edge, identical root membership/hash, and independent delta zero.
DT-06 Sparse 2–4-gram input reports sparse output and creates no candidate automatically.
DT-07 DF counts source versions; ISF separately recomputes same-claim available supporting role/class families and collapses mirrors/revisions/derivatives under the profile’s named rule.
DT-08 External PDF/OCR import retains exact input/output hashes, procedures/tools/config/environment, spans, quality, warnings, and uncertainty.

Domain and Semantic Negative Tests

ID Required result
DS-01 Generic software and IC/UVM “verification” remain distinct definitions/schemes.
DS-02 Construction/BIM digital twin is excluded from cid or retained only in an explicit ext scheme.
DS-03 Coverage/closure co-occurrence remains an observation; it creates no semantic predicate.
DS-04 Facet/scheme membership creates no hierarchy automatically.
DS-05 Identical external labels with different definitions cannot produce exact mapping.
DS-06 Model/rule relation suggestions remain candidates until an admissible separately reviewed claim exists.
DS-07 An accepted isolated VLSI concept remains in the published node inventory.
DS-08 Database/OAuth/build text in a VLSI container is not admitted by container location.
DS-09 Telecommunications text with shared labels remains outside cid absent exact VLSI applicability.
DS-10 Brazil/geography/policy text remains metadata, explicit ext, or excluded.
DS-11 A projected edge alone cannot enter reviewed_semantic_graph or satisfy a semantic release claim.
DS-12 Annotation/review/decision evidence or an informative warrant relabeled as qualifying E-DOMAIN/E-PROJECT is rejected; informative E-DOMAIN contributes to no count, ISF, reviewed graph, or release gate.
DS-13 Explicit cid scope, a cid predicate, or either cid endpoint activates one identical claim firewall; cid activation forces exact active cid scope, while scope none requires a sealed non-semantic profile.

Structural and Logical Checks

ID Required result
SL-01 All release IDs are unique, typed, immutable, live, and resolvable; every tombstoned stable ID remains reserved.
SL-02 JSON fields parse; SQL foreign keys, checks, unique indexes, typed-ID triggers, transition guards, and append-only guards reject malformed writes.
SL-03 Claim type/version equals the exact recomputed seal of a profile with at least one positive requirement; every group and ISF floor recomputes from exact qualifying same-claim evidence; every independence link names that claim/evidence and matching rule.
SL-04 Every n-gram has exactly n ordered token memberships from position zero through n-1.
SL-05 Every aggregate, observation edge, and similarity signal exposes coherent exact evidence/source/segment membership and its membership hash recomputes.
SL-06 Every semantic edge uses a registered non-obs predicate and its exact accepted admissible claim.
SL-07 Every mapping references the actual owning source/target concept scheme versions, crosses distinct versions, and retains intended/prohibited use, conditions, comparison rationale, and loss.
SL-08 Observation, candidate, claim, semantic, retrieval, V&V, approval, publication, and lifecycle records remain separate and are joined only by typed links.
SL-09 Every release item resolves its declared family/version and exact canonical record/hash; the immutable content manifest equals its packaging artifact identity/output; every item remains live and every live graph node is included before approval.
SL-10 Publication binds the exact approved current-head package hash and current gates/inputs/role separation. First success is a no-rollback bootstrap with evidence; later success advances from the immediate effective same-channel release; rollback proves immediate current and prior-success target history and restores only a target whose previously published package remains its valid current head.
SL-11 View and release exports are stably ordered canonical JSON/TSV with SHA-256 sidecars; release export accepts only a currently published release whose exact publication-bound package remains the current valid head, and emits both identities plus frozen snapshots.
SL-12 Each source-to-observation derivation declares exactly the artifact versions selected by the operation; missing or extra run inputs are rejected before records are written.

Retrieval and Intended Use

ID Required result
RU-01 The versioned query set covers supporting sources for SystemVerilog/UVM concepts, coverage distinctions, lifecycle artifact roles, DFT/test access, relation evidence/counterevidence, deprecated historical terms, and concept evolution without assistant-to-user leakage.
RU-02 Two VLSI/EDA reviewers independently judge a stratified sample; disagreement/adjudication, per-query precision/recall, macro/micro summaries, unanswerable queries, provenance errors, semantic false positives, and reviewer disagreement are retained.
RU-03 Semantic performance thresholds are set only after a baseline run, while the fixed release gate remains zero known provenance-class or domain-boundary violations.

Lifecycle and Release

ID Required result
LC-01 Unresolved changed dependencies make affected claims stale and block a new release/use; history remains unchanged.
LC-02 A changed intended use/query set or later not-fit result requires a new current validation head; prior validation remains historical and cannot satisfy a gate.
LC-03 Superseded/withdrawn standards open change/impact work; claims never silently rebind.
LC-04 Live claims/mappings/published dependencies block retirement.
LC-05 Tombstoned IDs cannot be assigned to a new term, concept, claim, evidence item, or release.
LC-06 Failed publication has no state-changing fields and does not change current release; advance names the immediate effective prior release; rollback proves the rolled-back release was current and restores only a prior same-channel success whose published package remains its valid current head; effective events use strict (event_time, publication_event_id) order.
LC-07 Superseding an intended use, query set, relevance baseline, validation, or retrieval evaluation immediately makes older fitness evidence non-current; release requires matching user group/context and current sealed bindings.
LC-08 The first effective same-channel success is possible only as bootstrap with evidence and no rollback fields; bootstrap is impossible after effective history, and every later success is advance from the immediate current release.
LC-09 Release content remains immutable after V&V; separate immutable approval-package versions freeze current evidence in one explicit non-forking supersession chain, and approval/publication bind only the current head’s hash rather than mutating or substituting the content manifest.

Non-Functional Controls

ID Required result
NF-01 In a clean supported Python environment, installation and every local command require only Python standard-library modules and SQLite and make no network request.
NF-02 Byte-identical clean inputs, configuration, explicit IDs, and timestamps produce byte-identical canonical rows, exports, and hashes.
NF-03 Malformed direct and workflow writes are rejected by the applicable foreign key, check, unique index, typed-ID trigger, transition gate, or append-only guard without altering prior rows.
NF-04 Missing, unavailable, partial, uncertain, and inconclusive values remain distinct from zero, pass, fit, approved, accepted, or published in records and exported views.
NF-05 Source and export path traversal outside configured roots is rejected, and database/generated operational state remains under configured app-local roots.
NF-06 Adversarial ingested text containing shell, SQL, Python, template, or configuration syntax remains inert data and is never dispatched for execution.
NF-07 User, assistant, quotation, file, code, tool, system, and external origin classes remain separately filterable in measures, evidence, views, and exports.
NF-08 Supersession, failed publication, rollback, deprecation, and retirement preserve all prior versions and successful historical releases as resolvable immutable records.

Suggested Operator Protocol

After independent review of the fixture content, an operator may initialize a disposable database, load the bootstrap, instantiate each fixture case, execute narrowly scoped validators first, then validate all, compare canonical exports across clean runs, and retain logs/hashes as E-CHECK. That future execution—not this source delivery—establishes pass/fail evidence.
