New-Record Transitions

“Promotion” is not a command or mutation. Each successful gate permits creation of a different immutable record:

From Explicit command New record
source segment pipeline normalize/tokenize/ngrams/aggregate/observe derivation, artifact, occurrences/measures/observation
observation workflow nominate-term or nominate-relation candidate + exact observation links
profile + positive requirements workflow seal-profile immutable canonical profile seal
query set + cases + judgments workflow seal-query-set immutable relevance-baseline seal
candidate/review package workflow claim atomic claim + typed evidence/use/candidate links + proposed event
proposed claim workflow review review + reviewed-accepted/rejected event
accepted claim set workflow release immutable release-content candidate/artifact/item snapshots/hash
checked release candidate/current package workflow finalize-release next immutable post-V&V package version + complete baseline snapshots
finalized package workflow approve independent decision + explicit typed inputs
approved package workflow publish publication attempt event
changed baseline workflow change then impact request/events + dependency closure + stale events/obligations
approved deprecation workflow deprecate validity/replacement/migration record
completed impact + approved retirement workflow retire retirement decision + tombstone

Claim State

(none) -> proposed
proposed -> reviewed_accepted | reviewed_rejected | superseded
reviewed_accepted -> stale | superseded
stale -> reviewed_accepted | reviewed_rejected | superseded

Rejected and superseded versions are terminal. A changed proposition normally receives a new claim version; a stale unchanged proposition can receive a new review event after its impact obligations are completed. current_claim_state selects the latest timestamp/event ID deterministically.

Change Request State

(none) -> open
open -> accepted | rejected | closed
accepted -> implemented | closed
implemented -> closed

The request row remains immutable; current_change_request_state derives state from events.

Release Gate

An approvable release must have:

  • at least one immutable item whose canonical record/hash recomputes, plus a non-recursive release-content manifest equal to the packaging artifact identity/output hash;
  • all graph nodes, including isolates;
  • only reviewed-accepted claim versions and semantic/concept records present in the exact reviewed graph;
  • exact sealed non-vacuous claim profiles, same-claim ISF, normative/authoritative typed warrants, the unified cid activation firewall, identity, and provenance;
  • a current pass/waived verification head against the exact release/version;
  • at least one current approved intended use for every included claim, exactly one current sealed query/relevance baseline per use, a current matching retrieval result, and a current fit/conditional validation head bound to the use version, user group, operational context, query version, and relevance hash;
  • a satisfied assurance argument with all required roles; and
  • no missing/tombstoned item, wrong record family/version, invalid projection/node, or omitted live graph node.

After those checks, finalize-release freezes the complete deterministic release-relative baseline closure in a separate canonical approval-package artifact. It does not mutate the release manifest. The first package for a release has no predecessor; every later package names the ordered current package head, so the immutable chain cannot fork. Only the current package head is eligible for a new approval or publication. The approver is independent of assertion, accepted review, and current V&V executor acts reached through all included claims, including claims backing concepts, assertions, and mappings. Approval inputs are explicit current links and include each current accepted claim review before publication; approval neither writes files nor changes current release. Later superseding use/query/V&V/retrieval records invalidate older package fitness immediately and require a superseding package version before another approval/publication attempt.

Publication Outcomes

  • successful bootstrap: permitted only when the channel has no earlier effective event; exact approved package hash, explicit bootstrap evidence, current package gates, publication procedure, event evidence, and publisher/approver separation are mandatory, while every rollback field is null.
  • successful advance: permitted only after bootstrap/effective history; it binds the exact approved package hash and names the immediate effective current release as its distinct rollback release, which must have succeeded earlier on that channel; rollback procedure/evidence and all normal gates are mandatory.
  • failed: exact approved package binding and event evidence are mandatory; bootstrap/rollback state fields are null and current release is unchanged.
  • rolled_back: the event’s release must equal the immediate effective current release; its distinct target must have succeeded earlier on the same channel using the package that remains that target release’s valid current package head; exact outgoing-package binding plus rollback procedure/evidence are mandatory.

current_published_releases selects the latest effective (succeeded or rolled_back) event per channel by (event_time, publication_event_id). For rollback state, it resolves both the restored release and that release’s latest earlier successful approval package rather than treating the rollback event’s package as the restored package. Current package eligibility is evaluated against this effective channel head; immutable historical publication rows retain their original structural validity instead of being retroactively reclassified when a package is superseded. A new effective event must be strictly later under that ordering. Failed events are audit evidence only and carry no rollback fields.

Impact and Staleness

workflow impact begins with changed items, expands known claim/evidence/release/intended-use dependencies, merges declared dependencies, hashes the closure, and stores each impact item. Open/blocked assessment creates stale events for previously accepted dependent claims. The assessment selects reverify, revalidate, both, or neither_with_rationale; one cannot substitute for the other.

Deprecation and Retirement

Deprecation preserves identity, history, retrieval treatment, validity, replacement, rationale, and migration plan. Retirement is blocked until impact is complete, exact retirement approval exists, and live semantic/mapping/published-release dependencies are removed or dispositioned. A successful retirement creates a tombstone; the target stable ID remains resolvable forever and cannot be reused.
