Updated

Primary Domain

cid: is limited to VLSI/IC design, verification, and test: relevant artifacts, activities, methods, tools, languages, representations, metrics, lifecycle stages, concerns, and evidence. A repository path, organization, project container, co-occurrence, or shared label is never sufficient admission evidence.

Independent Namespaces

Namespace Owner Permitted role
cid: Versioned internal CI-DIGITAL VLSI concept scheme Reviewed VLSI/IC design, verification, and test concepts.
ext: Independently versioned external scheme External meanings retained with original authority and version.
ifc: Versioned internal interface scheme Provenance, storage, query, graph, NLP, formal-semantics, and tooling concepts used to implement the index.

Concept records enforce the owning scheme version. A relation across schemes is an explicit mapping with intended/prohibited uses and loss; it is never a silent merge.

cid Admission

Every cid segment and concept needs:

  1. a preregistered stable target ID;
  2. one domain_applicability_record whose target ID/type match the target’s live stable-identifier type exactly;
  3. an exact non-empty locator and at least one normalized typed VLSI facet row;
  4. a declared basis with its required support: available E-DOMAIN for domain authority, available E-PROJECT for project requirement, reviewer for review, and available typed domain/project evidence + reviewer + rule for conditional external use;
  5. an admission_decision referencing that exact applicability record and target;
  6. decision_outcome='accepted'; and
  7. a scope decision whose registry namespace is cid.

The code resolves scope by registry namespace, not a hardcoded applicability identifier. For claims, one activation definition is used by insertion guards, views, validation, review, release, and publication: scope_namespace='cid', a predicate registered in namespace cid, or either endpoint resolving to a cid concept. Any activation forces an exact active cid concept-scheme version and claim-level applicability/admission. Scope none is allowed only for an explicitly non-semantic sealed profile. A later reclassification is a new decision linked through supersedes_admission_decision_id.

Qualifying Support

  • E-DOMAIN is valid only when it names a typed domain_warrant bound to a versioned external scheme, the same authenticated source version, exact locator, normative or authoritative status, and applicable scope. An informative warrant is retained as provenance but excluded from admissible support, counts, ISF, and reviewed graph/release gates.
  • E-PROJECT is valid only when it names an approved versioned requirements row.
  • Annotation, review, approval, publication, source frequency, and graph topology cannot be relabeled as either class.
  • A claim profile binds support role and evidence class; domain/project alternatives share one requirement group.

VLSI Facets

Facet membership is multi-dimensional, not a forced hierarchy. The accepted facet types are normalized in domain_applicability_facets; JSON is only the canonical envelope, not the release gate:

  • lifecycle/activity: requirements, RTL design, synthesis, physical implementation, simulation, formal verification, DFT, ATPG, manufacturing/post-silicon test, debug;
  • physical design/signoff: floorplanning, placement, CTS, routing, extraction, STA, SI, EM/IR, DRC, LVS, ERC, signoff;
  • artifact: specification, HDL, assertion, testbench, coverage model, netlist, floorplan, constraint, layout, result, fault model, pattern, waiver, defect;
  • verification/test method: inspection, lint, simulation, assertions, proof/model checking, equivalence, emulation, FPGA prototype, coverage, scan, boundary scan, IJTAG, BIST, ATPG;
  • concern: functionality, timing, power, area, integrity, CDC/RDC, mixed signal, reliability, security, manufacturability, testability;
  • evidence role: requirement, assumption, procedure, configuration, expected/observed result, proof, coverage, anomaly, disposition.

Facet membership never automatically creates broader, part-whole, causal, equivalence, or scheme-membership semantics.

Qualifying E-DOMAIN/E-PROJECT support is required for every claim activated by explicit cid scope, a cid predicate, or either cid endpoint. Interface/external claims do not become VLSI claims merely because they use a claim type shared with cid.

Binding Negative Rules

  • Generic software “verification” and IC/UVM verification remain distinct definitions.
  • Telecommunications material remains outside cid without exact IC applicability; words such as network or channel do not bridge the boundary.
  • Brazil/geography/policy is metadata, ext, or excluded—not a VLSI concept because of sponsorship or co-location.
  • Construction/BIM “digital twin” remains outside cid absent separately evidenced IC use.
  • Database, OAuth, build, graph, NLP, and formal-logic implementation concepts belong to ifc unless an exact independent VLSI meaning is admitted.
  • Visual clustering, adjacency, and projection remain presentation/observation evidence.

The non-negotiable pilot gate is zero known provenance-class or domain-boundary violations.
