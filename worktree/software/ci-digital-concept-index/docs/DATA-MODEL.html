Canonical Store

SQLite is canonical. JSON and TSV are downstream snapshots. Every JSON-valued column stores canonical explicit JSON; comma-packed identifiers are prohibited. Every typed entity also appears in stable_identifiers with a constrained entity_type.

Identity Model

  • A stable ID identifies one immutable version record, not a mutable logical object.
  • Logical continuity uses *_key + version, supersedes_*, validity intervals, or state-event links.
  • Every typed insert requires the same ID/type to be preregistered and live; Python registers it in the same transaction.
  • stable_identifiers cannot be deleted. Its only permitted update is the tombstone time caused by a matching tombstone trigger.
  • A tombstoned ID remains resolvable and cannot be registered under any type again.

Acquisition and Derivation Invariants

  • An acquisition artifact has exactly producer_kind='acquisition', one acquisition activity, and no derivation run.
  • A derived artifact has exactly producer_kind='derivation', one derivation run, and no acquisition activity.
  • Artifact identity is explicitly available with a hash or unavailable with a non-empty rationale; null never silently means either state.
  • Every selected configuration is explicitly applicable to the procedure and every linked tool used by its acquisition, derivation, verification, or validation act.
  • Every successful derivation has input and output links plus tool versions or an explicit no-tool rationale. Each input records the exact observed identity state/hash/unavailable rationale; no field is inferred from the current artifact row.
  • Every concrete derived row’s artifact_version_id and derivation_run_id match both artifact_versions and derivation_run_outputs; the output hash equals the artifact identity hash, including the explicit unavailable state.
  • Every source version’s artifact producer matches its acquisition_activity_id.
  • Source authentication/completeness and payload hash match that acquisition activity and artifact identity; routing changes form an immutable reviewed supersession chain.
  • Extraction binds exactly extraction_run -> derivation input/output -> extracted_text -> span -> segment; each segment’s required span covers its complete half-open range. The UTF-8 byte hash is a typed artifact_content_identity bound to output artifact/run/content role and is not equated to the extraction bundle’s identity hash.
  • Every release item’s stored canonical JSON and hash recompute from the exact typed record. The release manifest is the identity/output hash of a non-recursive content artifact containing release metadata and item snapshots.

Evidence and Warrant Invariants

  • E-SOURCE binds an authenticated source version or a segment from it.
  • E-DERIVED binds the exact artifact producer run and registered output.
  • E-DOMAIN requires domain_warrant_id; the warrant binds an external scheme version, authenticated source version, exact locator, scope, normative/authoritative status, and optional source segment. Informative warrants remain records but never qualify.
  • E-PROJECT requires project_requirement_id; the target requirement version must be approved.
  • Other evidence classes cannot populate those warrant fields.
  • Aggregate, edge, and similarity hashes are recomputable from normalized memberships; any supplied evidence item, source version, and segment must be the exact same provenance chain.
  • A projected edge copies the complete source membership, keeps the same membership hash, records its source edge, and has independent evidence delta zero.

Claim Profiles

Each claim binds claim_type_profile_id + profile_version + claim_type and requires a matching immutable claim_profile_seal. A seal canonicalizes the profile plus all requirements and is permitted only when at least one requirement exists and every minimum is positive. Profile requirements use requirement_group:

  • rows in one group are alternatives (E-DOMAIN or E-PROJECT);
  • different groups are cumulative (corpus_occurrence and vlsi_warrant);
  • each alternative states support role, evidence class, minimum count, and optional independent count;
  • minimum_isf is an additional profile-wide floor.

An independence association is append-only in claim_evidence_independence_links; its assessment must name the same claim and include that exact evidence item. Release gates recompute ISF from available, accepted, supporting evidence in the exact profile role/class and under the profile’s named rule; stored assessment-wide isf_value is not trusted as the gate result.

Scheme Model

  • concept_schemes and versions own internal cid and ifc namespaces.
  • external_schemes and versions own ext concepts.
  • A cid/ifc concept names exactly one matching internal scheme version and no external scheme.
  • An ext concept names exactly one external scheme version and no internal scheme.
  • A mapping’s source and target scheme-version IDs equal the actual owning internal/external scheme versions of its concepts; it also states conditions, intended use, prohibited use, and information loss.
  • Claim-level cid governance is active when scope_namespace='cid', the predicate namespace is cid, or either endpoint resolves to a cid concept. Every such claim must use an active cid concept-scheme version; scope_scheme_type='none' is reserved for sealed non-semantic profiles.

Release and Approval Identity

  • releases.manifest_hash is immutable release-content identity and is finalized before V&V.
  • release_approval_packages are separate derivation artifacts created after current verification, validation, retrieval, and assurance exist. package_version plus supersedes_approval_package_id creates one ordered, immutable, non-forking chain per release, exposed by current_release_approval_packages. Each package’s snapshots exactly equal the deterministic release-relative closure of definitions, labels/forms/facets, semantic relations/predicates, mappings, sealed profiles/constraints/rules, approved uses, sealed query/relevance material, and current V&V/retrieval/assurance records.
  • approval_decisions and publication_events bind one exact current-head package ID; publication_events.attempted_manifest_hash carries that approval-package hash, not the release-content hash.

Derived State

current_claim_state, current_change_request_state, current_source_routing, current_verification_records, current_intended_uses, current_query_sets, current_retrieval_evaluations, current_validation_records, current_release_approval_packages, governed_item_state, current_published_releases, and published_claims are views over immutable events or supersession chains. Current state is never inferred from an older pass/fit, use/query/package version, claim row, or approval alone.
