Making a UART failure tell a clearer story

Author

Fernando Lessa Magalhães

Updated

September 14, 2026

A first example from AI-Pipeline Tools for VLSI Workflows.

A UART test sends a byte. The receiver returns a different one. The simulation log records the mismatch, while a separate waveform records what happened inside the design. Explaining the failure means bringing those two views together.

That small gap in a custom workflow is where this C++ helper belongs. It connects a reported failure to the corresponding signal values, producing a compact, readable account that can become part of a technical report or a classroom explanation.

One question, two sources

The question is concrete: what did the signals show when the test reported the wrong byte?

vcd_snapshot.cpp reads a saved simulation log and a VCD file—the text format used here to record waveform changes. It takes the timestamp, expected byte, and received byte from a selected mismatch in the log. It then finds the requested signals in the waveform and prints their values alongside that failure.

The detail that makes this useful is temporal: a waveform stores changes, so a signal may have acquired its value before the failure was reported. The helper follows each selected signal to its latest recorded change at or before the requested time. Its built-in UART signal groups bring the configuration, serial interface, receive logic, and receive register into the same account.

The case it helped present

The saved UART boundary test records eight matching items at baud code 24. The first item at code 25 then fails:

Part of the recorded event Value
Test configuration Baud code 25
Expected byte 0x37
Observed byte 0x9b
Scoreboard timestamp 559615000

The correlation process uses this exact event as its worked example. Its companion waveform guide identifies the signals that show the transmitted byte, the receiver’s output, and the stored receive value.

Together, these conclusions give the failure a form an audience can follow: a selected configuration, an expected result, a different observed result, and the internal state associated with that moment. The results report describes the boundary exposed by the test. A snapshot helps examine that result; the timing sequence still matters when explaining its cause.

How the tool took shape with AI

The archived development conversation from April 22, 2026 records the choices behind the helper. The first requirement was to connect the scoreboard’s expected data with waveform state at a timestamp. The second was that it run standalone, so that someone reviewing the submission would not need the Task runner.

An initial Python approach prompted a discussion of implementation options. A compiled binary was preferred; C and C++ were compared, and light OOP in a single executable was selected. AI assistance turned those choices into source and refined it against the saved example. The development record preserves two practical corrections: accepting the spacing used in waveform signal names and selecting an actual mismatch instead of an earlier successful comparison.

The subsequent recorded run brings the two sources together: the report shows expected 0x37, observed 0x9b, and 0x9b in both the receiver output and stored receive data at the selected timestamp. This is the historical outcome behind the example above.

How the work becomes documentation

The comments are written in ordinary language and explain the intent, approach, and small OOP structure. The source’s opening explanation and component comments carry the reasoning behind the arrangement alongside the code that realizes it.

The executable contributes a formatted report of the timestamp, mismatch, and selected signal values. A later request for documentation and help led to the process guide explaining how to use that output in the submission. AI participation spans implementation, refinement, explanation, and preparation of material another person can understand.

The outcome is a small, independent example of AI helping create a useful process inside VLSI verification work. Its contribution to the wider line is easy to recognize: an engineering question becomes a focused tool, and the tool’s output helps make the work explainable.
