Local language tooling: capabilities and boundaries

Author

Fernando Lessa Magalhães

Updated

September 14, 2026

This note records the language-oriented tools observed on the current CI-DIGITAL workstation. It distinguishes what each kind of tool does, where the capability lives, whether it can be used without VS Code, and what has actually been verified.

The inventory is a local snapshot from September 13, 2026. It is not a claim that every installed component is active in every editor session, and it is not an upstream maintenance assessment. No software was installed while producing this inventory.

One word should name one role

Several tools can report a red underline, but they do not necessarily perform the same operation.

Term Primary role Typical result Usually changes source?
Syntax highlighter Classifies tokens for display Colors and text scopes No
Language server or language service Maintains a semantic model for an editor Completion, hover, navigation, symbols, references, diagnostics, and sometimes formatting Usually no; code actions and formatting may propose or apply edits
Linter Checks source against static rules Diagnostics with locations and explanations No by default; some linters offer explicit fixes
Formatter Rewrites layout according to a style Indentation, spacing, line wrapping, and brace placement where supported Yes when its result is accepted or written
Compiler Translates source and checks the language while doing so Object code, an executable, and compiler diagnostics It normally creates build artifacts, not source edits
Interpreter Evaluates source directly Program behavior, output, and runtime errors It can cause any side effects permitted by the program
Solver Searches for a model, proof result, or satisfying assignment sat, unsat, unknown, a model, or solver diagnostics No source edit by default

These are roles, not mutually exclusive product categories. One implementation may supply several roles. Tcl LSP, for example, provides language-server features, diagnostics, and formatting. A compiler can also supply diagnostics that an editor presents like lint results. LSP is a communication protocol; not every editor language service uses it.

Where a capability can live

VS Code presents one interface over several distinct execution layers:

  1. Built into VS Code. The editor ships and updates the implementation.
  2. Bundled by a user extension. The extension contains its own server, parser, formatter, or solver.
  3. Supplied externally. The extension is only a client or wrapper and expects a separate executable.
  4. Installed on the Fedora host. A terminal, script, or local agent can call the executable without VS Code.

The current VS Code installation is a Flatpak. Its extension host does not inherit the Fedora host’s normal executable path. An executable can therefore be present and directly callable on Fedora while still being invisible to an extension. The integrated terminal’s host-shell configuration does not change the extension host. External-tool extensions need an explicit path, wrapper, or flatpak-spawn --host bridge.

This creates four useful verification states:

  • Declared: a setting or extension manifest advertises the capability.
  • Present: the required component exists in its execution environment.
  • Reachable: the intended caller can start it.
  • Exercised: it has processed a representative file or command successfully.

An extension entry in Settings proves only the first or second state. It does not, by itself, prove that a backend is reachable or working.

Available bridge patterns

Flatpak is one present client boundary, not the target architecture. The broader objective is to make verified local tools available to editors, agents, command-line workflows, and other authorized clients. There is no single universal bridge, but four patterns are technically sound:

Pattern When it fits Tradeoff
Install the backend inside Flatpak The package or a compatible Flatpak SDK extension exists Simple for the editor, but it creates a second installation that can drift from the Fedora host
Use a flatpak-spawn --host wrapper The extension accepts a configurable executable or command Reuses the authoritative host installation; the wrapper and Flatpak permissions must be explicit
Connect to a server through TCP or a Unix socket Both the language server and editor client support a network address Clean process separation, but LSP support over a socket is implementation-specific and socket visibility must cross the sandbox
Install the upstream standalone tool in both environments Exact isolation is desirable and duplicate management is acceptable Predictable within each environment, but versions must be checked independently

The reverse direction is also possible when an extension bundles a tool that is published separately: install the upstream command on Fedora and use that public interface from terminals and automation. Depending on a private binary inside an extension is fragile because its path, permissions, and version belong to the extension’s packaging rather than to the host toolchain.

For this workstation, an authoritative editor-independent interface should be the default. An editor-specific wrapper can consume that interface when needed. A bundled engine remains appropriate when it is self-contained and already works, as with the current Tcl, Prolog, and SMT extensions.

Candidate editor-independent service boundary

The common service should not automate VS Code. It should expose the public interfaces of the underlying tools, allowing VS Code, local agents, scripts, and other clients to become peers.

Backend Verified native interface Smallest safe adapter
Tcl toolchain CLI accepts files, directories, or inline source; diagnostics can be JSON; rewritten source goes to a selected file or standard output Supervised one-shot process for validate, lint, format, graphs, and other batch operations
Tcl MCP MCP protocol over standard input/output Direct MCP connection for agent clients
Tcl language server LSP JSON-RPC over standard input/output Persistent per-workspace process only when completion, navigation, or live diagnostics are needed
SWI-Prolog CLI accepts source files and explicit goals; the host also supplies libswipl One-shot CLI for bounded queries; a persistent Prolog service only for an explicitly stateful use case
Z3 CLI accepts SMT-LIB files or standard input and returns solver results on standard output One-shot solver process with time and memory limits
GCC, G++, GNU Fortran, and TypeScript compiler CLI accepts project or source inputs and reports through exit status and output streams Isolated compile/check job with an explicit artifact directory
gofmt, AStyle, HTML Tidy, and xmllint File mode and/or standard input to standard output Transform request that returns proposed text or a diff instead of overwriting the caller’s file
Extension-private engines Internal extension process or protocol Do not use as the shared boundary unless the same engine publishes a stable standalone interface

MCP is a good client-facing protocol for agent tools. A small HTTP, Unix-socket, or ordinary command interface can serve non-MCP clients. The backend adapter does not need to use the same protocol: it can translate one bounded request into a CLI process, an LSP session, or a solver invocation.

A minimal request needs:

  • Operation: validate, lint, format, compile-check, interpret, or solve.
  • Language and dialect.
  • Source text or an explicitly bounded set of files.
  • Tool-specific options and resource limits.
  • Whether generated artifacts are permitted.

A useful response needs:

  • Exact tool identity and version.
  • Exit status and elapsed time.
  • Structured diagnostics when available.
  • Preserved standard output and standard error.
  • Proposed rewritten source or a diff, never an unannounced write.
  • Explicit artifact paths when compilation is authorized.

Rootless Podman is feasible as a packaging and isolation layer, especially when a backend is large, has conflicting dependencies, or should be reproducible for other users. Batch tools should normally start on demand and exit. Language servers may remain alive per workspace because their value comes from maintaining an index. In either case, use read-only source mounts by default, a scratch output directory, no network unless required, and CPU, memory, process, and time limits.

This separation also prevents a workspace-indexing language server from being treated like a trivial formatter. Both consume source, but the server may retain state and search an entire tree, while a formatter can usually be a stateless transformation of one document.

Microservice-like aggregation

The useful pattern is a stable front door with isolated tool workers, rather than one process that pretends every capability has the same semantics.

  • On-demand workers fit lint, format, compile-check, interpretation, and solver jobs that can be reproduced from explicit inputs.
  • Persistent workspace workers fit LSP servers and indexers whose value depends on retained project state.
  • Profiles bind a language or domain to a tool version, dialect, rules, limits, and permitted operations without merging those domains.
  • The evidence envelope gives every response common provenance fields while retaining the backend’s native output.

Containers make each worker reproducible, replaceable, resource-bounded, and deployable on another local or remote host. They do not require every worker to become a permanently running network service. Starting stateless workers on demand avoids idle resource use and limits the number of background indexers.

Fast responses come from keeping only the state that earns its cost: a cached capability registry, warm images, persistent indices for active workspaces, and event-driven invalidation when source or configuration changes. The broker may aggregate results, but it should not erase which tool, profile, version, and input produced each result.

This is intentionally microservice-like, not a conclusion that a large distributed microservice platform is already required. Container boundaries and common contracts provide most of the portability and isolation benefits. Network discovery, retries, distributed tracing, replicated state, and orchestration should be added only when a real remote or multi-host use case requires them.

Podman 5.8.4 is present on this workstation, so the container boundary is locally feasible. The architecture above is a recorded candidate, not an implemented service: no image, broker, socket, daemon, or remote endpoint was created during this inventory.

Current gaps

The following commonly expected backends were not found in the relevant host or Flatpak execution paths during this inventory:

  • Go language server: gopls.
  • Fortran language server and formatters: fortls, findent, and fprettify.
  • System-wide Clang language server and formatter: clangd and clang-format. The C/C++ extension has its own private formatter copy.
  • Rust language server and formatter: rust-analyzer and rustfmt.
  • Common standalone Python analysis tools such as Pyright, Pylsp, Ruff, Black, Mypy, Pylint, and Flake8.
  • Common shell and YAML tools such as Bash Language Server, ShellCheck, shfmt, YAML Language Server, and yamllint.
  • Alternative SMT solvers such as cvc5, Yices, Boolector, and Bitwuzla.
  • Separate Tcl linters or formatters such as Tclint, tclfmt, and Nagelfar.

“Not found” means that no usable executable was observed in the checked environment. It is not a claim about what Fedora could install or what exists upstream.

Tcl formatting and the Whitesmiths requirement

The project’s desired visual signature is specifically the placement and alignment of block braces in Whitesmiths style. It is not merely a tab choice or an indentation width.

The current Tcl formatter cannot produce that signature. Its only exposed brace style is k_and_r. It can normalize indentation and whitespace, but it leaves opening block braces at the end of their command line. Running it therefore does not satisfy the requirement even when the resulting body indentation changes.

Tcl also makes this more than a cosmetic substitution. An unescaped newline terminates a command, so blindly moving an opening brace to a line of its own can change or break the program. The official Tcl style guide states that an opening brace cannot appear alone and should remain at the end of the preceding line. The installed formatter’s formatting specification exposes only K&R brace placement.

A robust Whitesmiths feature for Tcl would therefore need all of the following:

  1. Tcl-aware parsing rather than a textual brace-moving rule.
  2. A semantics-preserving continuation strategy wherever a block brace moves.
  3. Coverage for Tcl 9 and each relevant embedded EDA dialect.
  4. Idempotence: formatting the result again must produce no further change.
  5. Execution or parser comparisons on representative scripts before adoption.

That feature is feasible, but it is not present today. Format-on-save remains disabled so the existing K&R-only formatter cannot silently erase the intended visual marker.

Tool routing for local, observable work

Deterministic local tools should answer mechanically checkable questions before an AI system interprets the result.

Question First tool AI contribution after the tool
Is this token sequence valid Tcl? Tcl parser/interpreter or Tcl diagnostics Explain the error in project context and propose a bounded correction
Does the source violate static rules? Linter or language-server diagnostics Correlate findings, distinguish signal from noise, and prioritize
Does layout match the selected style? Formatter plus a source diff Explain exceptional cases and verify that no unintended semantic edit occurred
Does C, C++, Fortran, Go, or TypeScript type-check or compile? Corresponding compiler/toolchain Interpret diagnostics and relate them to design intent
Is an SMT constraint satisfiable? Z3 Explain the model, assumptions, and limits of the result
What changed? Version-control diff and preserved command output Relate the observable delta to the stated requirement

This division reduces speculative work. A compiler or solver supplies reproducible evidence; AI is then used for synthesis, explanation, cross-domain reasoning, and carefully bounded changes. When provenance matters, retain the invoked command, tool version, input identity, raw result, and resulting diff rather than only a prose retelling.

The action footprint still matters:

  • Highlighting, navigation, and ordinary linting are read-only observations.
  • Formatting becomes a source mutation when its result is accepted.
  • Compilation normally creates artifacts even when it does not edit source.
  • Interpretation executes a program and can trigger its permitted side effects.
  • Solver execution is normally read-only with respect to the source, but its result depends on the exact assertions and solver version.

Evidence behind this inventory

The snapshot was assembled from observable sources rather than from extension names alone:

  • Host command resolution and version output.
  • Fedora package records for the host runtimes and compilers.
  • The VS Code Flatpak’s own shell view of executable availability.
  • VS Code’s extension registry and disabled-extension state.
  • Installed extension manifests, bundled files, and declared providers.
  • Current VS Code user settings.
  • Current Tcl LSP initialization logs.

The relevant VS Code state lives under the user Flatpak data and configuration directories. Built-in language features live under the active system Flatpak installation. Extension-private binaries are evidence of a bundled capability, not stable system interfaces.

Installed versions describe this workstation only. Before recommending a new dependency or treating one as a durable project choice, also verify its upstream release date, recent maintenance, supported language versions, and unresolved issues. That maintenance check was outside this local inventory and is therefore not implied here.

Rechecking the snapshot

The host inventory can be refreshed without VS Code:

command -v swipl z3 tclsh go gofmt gcc g++ gfortran tsc astyle tidy xmllint
swipl --version
z3 --version
printf 'puts [info patchlevel]\n' | tclsh
go version
gcc --version | head -n 1
gfortran --version | head -n 1
tsc --version

The Flatpak view must be checked separately. This example demonstrates the version boundary rather than changing it:

flatpak run --command=sh com.visualstudio.code -lc \
    'command -v gfortran; gfortran --version | head -n 1'

The final check belongs at the point of use: open or process a representative file, observe which implementation responds, retain its output, and avoid inferring an operational capability from a settings page alone.

Subsequent implemented container boundary

After the inventory and architectural candidate were recorded, a separate authorized step implemented the first container boundary at language-toolbox/. This changes the earlier statement about no image having been created; it does not promote the proposed broker, socket service, or remote endpoint into implemented components.

The image packages the editor-independent Tcl, Prolog, Z3, C, C++, Fortran, Go, JavaScript, TypeScript, HTML, XML, and C-like formatting tools behind one foreground entry point. It uses a digest-pinned Fedora base, exact direct RPM versions, checked Tcl release artifacts, and a version-pinned Go language server. The runtime lock records those inputs.

Verification established four distinct levels rather than collapsing them:

  • The image built from the recorded sources and package versions.
  • Every installed tool family processed a representative input under a read-only, network-disabled, capability-dropped container invocation.
  • Tcl LSP and gopls each completed a real LSP initialization exchange.
  • Tcl MCP and gopls mcp each completed a real MCP initialization exchange.

The resulting image is below 1 GB unpacked. That size is dominated by the actual compiler toolchains and three independent Tcl analysis executables, not by an editor or graphical environment. The exact image identity, size, checks, and remaining boundaries are retained in the build record.

This implementation does not yet connect VS Code to the container. The editor remains one possible client, while the image is already usable directly by Podman, scripts, or an agent. No repository source was formatted, compiled, or otherwise transformed as part of the container’s smoke tests.

Go is the selected implementation language for a later common broker or protocol adapter if that next layer is authorized. This is a forward implementation decision, not evidence that the broker already exists.
